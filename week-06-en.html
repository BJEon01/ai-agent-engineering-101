WEEK 06

Modern Protocols 2: Agent2Agent 현대 프로토콜 2: A2A

What does my agent have to exchange with someone else's agent to hand it a job? In week 05 the party receiving a request over MCP was a tool. In A2A (Agent2Agent) it is another agent. Without knowing which model or tools it uses, you read the self-description it publishes (its Agent Card), pick it, hand it the job as a task, and get the result back. The assignment changes only the sentences in an Agent Card and measures how that changes which shop a buyer agent hands the job to, and what deal it gets.

A1

MCP and A2A: calling a tool, handing over a job

In week 05 the host's model looked at the server's tool list and decided which tool to call with which arguments.

In A2A the party receiving the request is an agent. Send a shop agent “I want to buy a lamp” and the shop decides what price to ask, what to ask back, and whether to turn the deal down. The sender does not know which model the other side runs, which tools it calls, or what it remembers. The specification calls such a party opaque, and states the goal as agents working together “without needing access to each other's internal state, memory, or tools.”

FIG. 01 A2A between agents, MCP inside each agentdelegation crosses the boundary; tool calls stay inside it
MCP (week 05)A2A
Receives the requestA server's tool. Name, description, and argument schema are publicA remote agent. Describes what it can do (skills) in natural language
What you sendA tool name and arguments (tools/call)A message (SendMessage): text, files, JSON data
What comes backThe tool resultA task (state and results), or a single message
Decides howThe host's modelThe remote agent that took the job
Asking back midwayThe server returns an input_required result (week 05, A3)The task stops in TASK_STATE_INPUT_REQUIRED

Both protocols can ask back. The two are used together in one system: the shop agent takes orders over A2A and, to check its stock, calls tools on its own MCP server (FIG. 01).

A2A is a protocol for agents that cannot see inside each other to find one another (Agent Card), hand over work (task), and receive the results (artifact).

The examples and the lab in these notes were checked against the A2A v1.0 specification, the Python SDK a2a-sdk 1.2.2, and the official CLI a2a 0.3.0.

A2

A2A today: v1.0, AAIF, the official CLI

Since Google announced A2A in April 2025, both its home and its specification version have changed several times (FIG. 02).

FIG. 02 A2A, from announcement to AAIFthis note uses v1.0

In August 2025, IBM's Agent Communication Protocol merged into A2A. It shares only the acronym with the Agent Client Protocol of week 08.

v1.0, released in March 2026, is the first stable version. It added signed cards, multi-tenancy (several agents behind one address), and version negotiation through the A2A-Version header. Method names and the way state values are written also changed from v0.3, so v0.3 example code on the web does not work against a v1.0 server as is.

In August 2026, A2A became a project of the Agentic AI Foundation (AAIF) under the Linux Foundation. MCP from week 05 is an AAIF project too. AAIF describes its projects as layers: MCP connects an agent to tools, and A2A connects an agent to other agents (FIG. 03).

FIG. 03 Where A2A sits in the AAIF stacklayers as AAIF describes them, aaif.io

According to AAIF, more than 150 organizations support A2A; at launch there were more than 50 technology partners. These are the uses the announcement lists.

AreaExample
Mobile OSHuawei's HarmonyOS assistant Celia hands long-running tasks to agents inside apps and asks them for UI control and recommendations. WeChat uses this link for messages, voice calls, and video calls started by an AI assistant
CloudGoogle Cloud (ADK, Agent Engine, Cloud Run, GKE), Microsoft Azure AI Foundry, and AWS Bedrock AgentCore can host A2A servers and find other agents
PaymentsThe Agent Payments Protocol (AP2) from Google Cloud and PayPal. Shopping agents and merchant agents exchange products and prices over A2A, and AP2 handles payment authorization
FrameworksLangGraph, CrewAI, Pydantic AI, AG2, IBM BeeAI

These examples come from AAIF and the A2A project; these notes did not check how much each company actually uses A2A.

In October 2026 the project announced the official CLI, a2a. From a terminal it fetches cards, sends messages, and reads and cancels tasks. You do not have to write JSON-RPC requests by hand, so this week's lab uses it. The same repository has a skill that lets coding agents such as Claude Code, Cursor, and Codex hand work to remote A2A agents through the CLI.

The roadmap, last updated on September 15, 2026, lists these items.

The lab shop's bargaining rules (the opening price, the counteroffer, how many low offers before it walks away) are not in the specification; they live only in the shop's code.

A3

Agent Card: finding an agent to hand the job to

An A2A server MUST publish an Agent Card: a JSON document with the agent's name, description, the address that takes requests, the features it supports, and its skills. The default location is https://{domain}/.well-known/agent-card.json. This is the card of the shop agent you will run in the lab.

GET http://127.0.0.1:9999/.well-known/agent-card.json
{
  "name": "Lamp Shop",
  "description": "Sells desk lamps, chairs and bookshelves. Negotiates the price with the buyer.",
  "supportedInterfaces": [
    { "url": "http://127.0.0.1:9999/", "protocolBinding": "JSONRPC", "protocolVersion": "1.0" }
  ],
  "version": "1.0.0",
  "capabilities": { "streaming": true },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["application/json", "text/plain"],
  "skills": [
    {
      "id": "negotiate",
      "name": "Negotiate a purchase",
      "description": "Ask for an item, then send a price. The shop answers with a counteroffer or a receipt.",
      "tags": ["shopping", "negotiation"],
      "examples": ["I want to buy a lamp", "90"]
    }
  ]
}

supportedInterfaces lists where and how the agent takes requests. v1.0 defines JSON-RPC, gRPC, and HTTP+JSON (REST) bindings; the server lists the ones it supports in order of preference, and the client takes the first one it can use. The lab shop supports JSON-RPC only.

skills lists what the agent can do in words a person reads. Unlike a week-05 tool, a skill has no argument schema (JSON Schema). The client's model reads the description and the examples and decides what to send and how.

FIG. 04 Discovery, then the first messagethe card is a plain HTTP GET

Besides the well-known URI, a client can look a card up in a registry that collects cards, or use a card address configured in advance.

In FIPA, the Directory Facilitator (DF) of an agent platform did this job. Agents registered their services with the DF, and other agents searched the DF by service type (yellow pages). In A2A each agent puts its card on its own domain, and a registry is used when needed (FIG. 05).

FIG. 05 Directory Facilitator and Agent Cardthe directory became optional

Whoever builds the agent writes its card. So it was with the week-03 Contract Net bid and the week-05 tool description. In v1.0 a card can carry a JWS signature, so a client can check who published it and that it was not altered on the way. Nothing in the specification checks whether the sentences in a card are true. The assignment changes one card's sentences and measures the effect.

A4

Task: the state and the results of a delegated job

The client sends a message with SendMessage. If the server can answer right away, it replies with a single message; if the job takes time or needs back-and-forth, it creates a task and returns that. Send the lab shop “I want to buy a lamp” with the a2a CLI and a task comes back.

lab/logs/lab-cli.txt
$ a2a send -a http://127.0.0.1:9999 "I want to buy a lamp"
Task:     a7b1e3f3-9530-4eb2-b84c-cac830752ff3
Context:  8718ea6a-4c6d-4ccc-a416-57ff708de2f2
Status:   input-required (2026-10-13T05:21:00Z)
  lamp: asking 130. Send your offer as a number.
History:
  [user] I want to buy a lamp

Resume:     a2a send --task-id a7b1e3f3-9530-4eb2-b84c-cac830752ff3 "<reply>"

Task is the task number the server made; every later message about this job carries it. In the CLI you pass it with --task-id, and the last line, Resume, shows that command. Context groups related tasks and messages into one conversation. Status holds the current state and what the shop said, History the messages so far. When the job is done, its results are attached under Artifacts. Add -o json and the same content comes out with the specification's field names (id, contextId, status, history, artifacts) (FIG. 06).

FIG. 06 What a task carriestalk goes in messages, results go in artifacts

What the shop says (“80 is too low”) arrives as the status message; the outcome of the deal arrives as an artifact. The specification says results SHOULD be returned as artifacts, not in messages. Messages and artifacts are both made of Parts. A Part holds one of text, raw (file bytes), url (a file address), or data (a JSON value), and mediaType names the format. The lab shop's receipt is a data Part, so the receiving code reads price directly.

In JSON a task state value looks like TASK_STATE_INPUT_REQUIRED. The CLI shows it shortened, as input-required. That lower-case form was the actual value in the specification up to v0.3, so example code on the web that compares lower-case values in JSON targets v0.3.

StateMeaningKind
SUBMITTEDReceivedactive
WORKINGIn progressactive
INPUT_REQUIREDStopped, waiting for input from the clientinterrupted
AUTH_REQUIREDStopped, waiting for authenticationinterrupted
COMPLETEDFinished, successfullyterminal
FAILEDFinished with an errorterminal
CANCELEDFinished because the client canceled itterminal
REJECTEDFinished because the agent decided not to do the jobterminal

An interrupted task continues when the client sends a message with the same taskId. A terminal task takes no more messages; the server answers one with an error.

FIG. 07 Task lifecycle, A2A v1.0interrupted states wait for the client

FIG. 08 draws the lab purchase as state changes. The shop named a price and stopped to wait for input (INPUT_REQUIRED); when the buyer sent 80 with the same taskId, it countered at 105. When the buyer sent 105, it closed the deal (COMPLETED) and attached a receipt artifact. Sending 110 to the finished task returned UnsupportedOperationError: JSON-RPC error code -32004, shown by the CLI as UNSUPPORTED_OPERATION.

FIG. 08 One purchase, one tasklab/logs/lab-cli.txt

When a task runs long, the client chooses how to wait for the result. It can ask again with GetTask (polling), or keep a connection open with SendStreamingMessage and receive state changes as Server-Sent Events. If the client registers a webhook address, the server sends a notification there whenever the state changes (push notification). The server states in the Agent Card's capabilities whether it supports streaming and push notifications.

A2A also leaves out a place for the terms of a delegation. A task has nowhere to say how much may be spent, in whose name, or how the result will be checked. The lab buyer's budget lives only in the buyer model's system prompt. Week 07 builds a contract that carries these terms with the delegation and checks them.

DISCUSSION: Who checks what an Agent Card claims?
  1. In the assignment, South Shop's card says “lowest prices in town”. Of the client's model, a registry, a card signature, and reputation built up after deals, which can check that sentence? What is the same as the bid of week 03's overconfident contractor, and what is different?
  2. In A2A the shop agent decides whether to read “105” as acceptance. When is it better to send accept-proposal explicitly, as in FIPA? Answer from the results of week 04's tagged condition.
  3. The remote agent is opaque. When a deal goes wrong, the client's only evidence is the task history and the artifacts. Can you tell from those who was at fault? What else would you need?

Run a shop agent as an A2A server

GOAL: run a rule-based seller as an A2A server, take one purchase to COMPLETED with the a2a CLI, and reach REJECTED and CANCELED once each
LAB

Start Lamp Shop and trade with it using the a2a CLI

Start a shop agent that names prices by rule, with no model, using a2a-sdk; fetch its card with the official CLI and buy a lamp. No model is called, so no API key is needed. The shop opens at 1.3 times its reserve (the lowest price it accepts) and closes the deal when an offer reaches the reserve. A lower offer gets a counteroffer, and after three low offers the shop rejects the deal.

  1. Install. Install the server side with pip install "a2a-sdk[http-server]" uvicorn. Install the CLI on macOS and Linux with brew tap a2aproject/a2a-cli https://github.com/a2aproject/a2a-cli and then brew install a2a, or on Windows with winget install a2aproject.a2acli. go install github.com/a2aproject/a2a-cli@latest names the binary a2a-cli; rename it to a2a. The reference run used a2a-sdk 1.2.2, Python 3.12, and a2a 0.3.0. An SDK in another language is fine.
  2. Write the server. seller_agent.py. The execute method of an AgentExecutor runs once per incoming message and changes the task state through a TaskUpdater. The SDK's route functions build the card and JSON-RPC routes.
  3. Start it and fetch the card. python seller_agent.py serves on http://127.0.0.1:9999. In another terminal run a2a card get http://127.0.0.1:9999. The CLI reads /.well-known/agent-card.json and shows the name, the address, and the skills.
  4. Send without the header. The CLI adds the A2A-Version header for you, so send one request without it using the curl command below. The specification says a server must read a request without the header as version 0.3, and the lab server, which accepts only 1.0, rejects it with -32009 (VersionNotSupportedError).
  5. Buy the lamp. Send a2a send -a http://127.0.0.1:9999 "I want to buy a lamp". Following the Resume line at the end of the output, add --task-id and send 80, then 105. Once completed and the receipt artifact come back, run a2a task get: History holds 5 messages.
  6. Send to the finished task. Send 110 with the same --task-id; the CLI reports UNSUPPORTED_OPERATION and exits with code 1.
  7. Reach the other terminal states. Asking for a sofa, which the shop does not sell, ends rejected; offering 100 for a chair three times ends rejected; a2a task cancel on an open bookshelf task ends canceled.
seller_agent.py (the core)
class Seller(AgentExecutor):
    async def execute(self, context, event_queue):
        task = context.current_task
        if task is None:                                   # first message: create the task
            task = new_task_from_user_message(context.message)
            await event_queue.enqueue_event(task)
        up = TaskUpdater(event_queue=event_queue, task_id=task.id, context_id=task.context_id)
        say = lambda text: up.new_agent_message(parts=[new_text_part(text)])
        text = get_message_text(context.message) or ""
        deal = self.open.get(task.id)

        if deal is None:                                   # which item?
            item = next((k for k in self.cfg["reserve"] if k in text.lower()), None)
            if item is None:
                await up.reject(say("We only sell: ..."))        # REJECTED
                return
            ask = math.ceil(self.cfg["reserve"][item] * 1.3)
            self.open[task.id] = {"item": item, "ask": ask, "rounds": 0}
            await up.requires_input(say(f"{item}: asking {ask}. Send your offer as a number."))
            return

        offer = int(re.search(r"\d+", text).group())
        if offer >= self.cfg["reserve"][deal["item"]]:
            await up.add_artifact(parts=[new_data_part({"seller": ..., "item": ..., "price": offer})],
                                  name="receipt")
            await up.complete(say(f"Deal: {deal['item']} at {offer}."))   # COMPLETED
            return
        ...                                                   # counteroffer (INPUT_REQUIRED) or walk away (REJECTED)

    async def cancel(self, context, event_queue):         # CancelTask
        task = context.current_task
        await TaskUpdater(event_queue=event_queue, task_id=task.id, context_id=task.context_id).cancel()

The inflated Agent Card experiment: same shop, different card

Run two lab shops. The code and the items are the same; only the reserves differ. North Shop is cheap (lamp 100, chair 180, bookshelf 260), South Shop is pricey (lamp 125, chair 225, bookshelf 325). Both open at 1.3 times the reserve and turn the deal down on the fifth low offer. The buyer agent gets a budget in its system prompt, reads both shops' Agent Cards, picks one, and makes the same A2A purchase as in the lab, with at most 6 offers.

Between conditions, only the sentences in South Shop's card change. North Shop's card is the plain one in both conditions, and the order in which the buyer sees the two cards is randomized per episode.
